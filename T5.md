# T5 — sample scenario, record cleanup and privacy

T1–T4 capture, matching rules, permissions, decision transitions and optimistic concurrency are unchanged. New decisions add the issue/CAPA IDs to pair-state; old records are readable without these fields. Evidence cards now place `QualityLoop closure date: <date>` and `(Jira status: <status>)` on separate lines.

## Verified Forge contracts and limitations

The Forge MCP guides and API-operation/scope tools were used for both page modules, context, trigger filtering and event payload, issue creation (including properties), project/create-metadata issue-type lookup, issue reads/deletes, transitions, issue links, permissions, enhanced JQL, KVS queries/cursors/conditional writes/transactions, entity indexes and Forge storage retention.

Removed scope: **`manage:jira-configuration`**. Forge MCP `fetch-api-operation` and `get-api-required-scopes` verified that `GET /rest/api/3/issue/createmeta/{projectIdOrKey}/issuetypes` uses the existing **`read:jira-work`** classic scope and requires **Create Issues** permission in the requested project. Existing `read:jira-work`, `write:jira-work`, `read:jira-user` and `storage:app` remain; no scopes were added. Jira issue deletion uses the existing **`write:jira-work`** classic scope. No Jira configuration write is performed.

Sample preparation reads the current context project's create metadata through `asUser()`, supporting company-managed and team-managed projects and non-admin users who can create issues. It selects the first non-subtask type in metadata order, preferring a non-subtask type named exactly `Task`, including on later pages. Pagination uses documented `startAt`, `maxResults` (200 maximum), `issueTypes` and `total` fields. The confirmation dialog names the selected type; this is a selection policy, not a lookup of Jira's configured default. Empty or subtask-only metadata prevents preparation, metadata errors cannot save a plan or create issues, and HTTP 403/404 returns no data. Required custom fields and Jira validators can still prevent creation.

Jest coverage includes pure type selection, both project styles with creator-only API mocks, a preferred Task on a later page, fallback order, subtask exclusion, empty metadata, denied/error responses and creation using the selected project-specific ID. Live verification with non-admin users in both project styles remains an owner check.

Local verification after replacing the lookup: `npm test` passed all 20 suites / 187 tests; `npm run lint` and `npm run build` passed.

Forge creates/updates indexes after deployment, independently of code deployment, and documents a minimum indexing time of five minutes. Installation/upgrade must wait until indexes are ACTIVE. Adding indexes does not supply the new issue/CAPA attribute values in legacy pair-state objects. **Find orphaned records** scans the built-in `by-key` index and idempotently fills IDs from each validated pair key, preserving state/version and conditionally writing against the current version. Concurrent changes are deferred and counted; rerun the scan if backfill is pending. There is no manual data export or migration script to run. New writes already include both IDs. Forge documentation does not explicitly guarantee how a newly declared attribute absent from old objects participates in a new index; the by-key backfill and cleanup fallback avoid depending on that behavior.

The trigger subscribes to **`avi:jira:deleted:issue`**, with `filter.ignoreSelf: true`; it uses only app storage. Queries are eventually consistent; direct reads recheck current records. Cleanup is best effort and stops doing new work after its time budget, logging incomplete work. Sample removal separately scans records because self-generated events are ignored. Admin existence checks use `asApp()` only after a fresh `asUser()` Jira-admin check, as explicitly requested in T5; no Jira fields or summaries are returned. Only explicit 404s select records, and deletion checks again without the scan cache. Transactions contain at most 25 deletes.

A browser interruption does not automatically retry an ambiguous Jira create. IDs already returned by Jira remain registered for removal. If Jira created an issue but its response never reached the app, the UI warns that it cannot safely delete the unknown ID; inspect the sample label manually. A function interrupted while holding an operation lock may require waiting for Forge's TTL expiry cleanup before retrying. Extra required Jira fields may prevent sample creation; completed partial issues remain registered for removal.

No live Jira deployment, rendering, transition validators, event delivery, or index activation was verified locally. Forge CLI was not available on PATH or in the local npm bin directory, so `forge lint` could not be run here. No deploy/install/tunnel/login was run. The hidden evaluation split was not opened.

## Owner click/check sequence

1. As a Jira admin, open **Jira settings → Apps → QualityLoop data → Find orphaned records**. Let both entity scans finish. Check the backfilled/pending counts. Run again: backfilled should become zero, with no pending work. Existing decision history, pair versions and T4 concurrency checks must still work.
2. As a non-admin user with Browse Projects and Create Issues permissions, open a company-managed test project with no extra mandatory fields. In its project navigation, click **QualityLoop → Create sample scenario (5 issues)**. Verify the dialog names Task if a non-subtask Task is available, otherwise the first non-subtask type returned by create metadata, and lists all five records, fields/dates, the illustrative evidence URL, the historical relates-to link, transition attempts and storage write. Cancel once and confirm that no issues were created. Open it again and confirm. Repeat in a team-managed test project, and check a project without Task to exercise the fallback.
3. Wait for **Ready**, then open the linked new NC and its **qualityloop** panel. It should strongly match **DEMO CAPA-B**, with **No effectiveness evidence recorded at closure**. The decoy may appear in **Other related records**, never as a signature match. Check the two separate closure-date and Jira-status lines. Available Done transitions should have been attempted; otherwise the project page shows a note.
4. Open **DEMO historical NC**. Confirm it relates to CAPA-A, has a detected date before CAPA-A's QualityLoop closure date, and does not match CAPA-A. Check the five issues use the type named in the confirmation dialog and the `qualityloop-sample` label. The project page must contain no real defect data. A second scenario must be refused while its registration exists. Run a readiness check again if indexing exceeded 30 seconds.
5. Record a sample decision. Click **Remove sample scenario** and inspect its issue-key list; cancel once. Remove the sample label from the decoy, then reopen the removal dialog and confirm. Only registered, still-labelled issues should be deleted; the unlabelled decoy remains. Delete that decoy manually afterwards if desired. Verify matching app records are gone using the admin scan, and that a new sample can now be created.
6. Test removal with a user who can browse the sample but lacks Delete Issues permission. The page must report each visible issue it could not delete, leave it in Jira and clear the sample registration. Inaccessible issue keys must never appear. Remove any remaining sample issues manually before creating another scenario in this project.
7. Using disposable issues, create T4 decisions, then delete either the NC or CAPA through Jira. Allow the event to run; in **QualityLoop data**, scan to verify the associated decision/pair-state records were removed. If an event or storage call was missed, the scan should list orphan IDs and record IDs without summaries. Click **Delete orphaned records**, cancel once, reopen and confirm; scan again to verify. Jira issues must not be changed by this admin action. A 403/429/5xx must remain unresolved, never selected just because the check failed.
8. A non-admin should not see **QualityLoop data**, and direct resolver calls must return no scan/deletion data. Recheck T1–T4 capture, evidence access, human decisions, confirmed follow-up creation and concurrency using their existing checklists. No workflow, real CAPA status or real Jira issue should change during sample actions.
