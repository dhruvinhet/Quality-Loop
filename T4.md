# T4 — Read-only panel and engineer decisions

The panel checks `EDIT_ISSUES` as the current user on the context issue before
rendering. Non-editors see saved text, evidence, state, and history, with no
capture form or decision controls. Property saving still relies on Jira's
existing permission enforcement; its resolver behavior is unchanged.

Decisions re-authorise the CAPA asUser, check the current issue's edit permission,
and rerun the existing server-side matcher. Only an NC's current strong and
related-revision matches qualify. Issue and author IDs come from resolver
context. A concern requires either a confirmed pair or absent effectiveness
evidence. Payload fields are allowlisted and validated on the server.

## Storage and corrections

Forge entity names allow lowercase characters only. The logical `pairState`
entity is therefore named **`pair-state`**, keyed `<capaId>:<ncIssueId>`. The
`decision` entity uses `<capaId>:<ncIssueId>:<server-milliseconds>-<random-UUID>`.
Timestamp prefixes order IDs by creation time; UUIDs distinguish concurrent
writers. Server-generated ISO timestamps are used for index range values.

One `kvs.transact()` sets the pair and inserts the decision. The conditional
pair write uses `FilterConditions.equalTo(expectedVersion)` on `version`, or
`FilterConditions.notExists()` on `version` for version zero. Every persisted
pair has a version, so the latter admits only an uninitialised pair. The first
successful decision creates version 1. All write decisions read pair state
with `entity().get()`, which Forge documents as strictly consistent.

On a transaction error, direct reads reconcile the result: an existing decision
with this unique ID proves this write committed; otherwise a changed version
returns a conflict and the current pair state. An unchanged version propagates
the storage error. This avoids guessing a transaction-condition error code,
which the retrieved Forge error reference did not specify.

Each new CONFIRM, NOT_RECURRENCE, or CONCERN supersedes the previous state while
preserving history. **Correct explanation** records SUPERSEDE: it replaces the
explanation/evidence and preserves the existing state. There is no edit/delete
endpoint. Categories are required only on NOT_RECURRENCE. Reasons are required
and limited to 1000 characters; evidence is at most five HTTP(S) URLs without
credentials, at most 2000 characters each.

`decision.by-issue` partitions by `issueId` and ranges by `createdAt`;
`decision.by-capa` partitions by `capaId` and ranges by `createdAt`. Queries
follow every cursor. History re-fetches CAPAs asUser and omits inaccessible
ones. Counts include CONFIRM decisions since the CAPA's recorded closure and
also exclude inaccessible NCs. These are counts of decisions, not distinct
NCs, and remain display-only. The UI labels their eventual consistency. A
direct latest-decision read fills the immediate history gap while indexes
catch up. Former matches retain read-only history on the current issue.

## Concern follow-up

The concern commits before the follow-up dialog opens. The dialog lists:

> Create task in <CAPA project>: 'Effectiveness re-review: <CAPA key>' and link it to <CAPA key>

**Keep decision only** closes it without Jira writes. **Create task and link**
checks permissions again, resolves the project's standard Task issue type and
the site's symmetric `relates to` link type, creates the Task asUser, saves
`taskKey`, and links it asUser. It rejects a changed CAPA key/project rather
than changing the confirmed write. Project-specific required fields or missing
Task/link configuration can prevent this step; the decision remains recorded
and the error is shown. No fallback issue type or link type is substituted.

An optional internal `taskClaimId` attribute on the decision provides an atomic
claim for one follow-up attempt. Repeated calls do not create another task.
After any ambiguous response, inspect Jira before manually arranging another
follow-up. A created task key remains stored even if linking returns an error.
Task links in history are shown only if the viewer can browse the task.

## Owner commands, in order

Use Node.js 22.x or 24.x. These target the existing development installation;
select its site/product when prompted. Only the owner deploys or installs.

```powershell
npm ci --legacy-peer-deps
npm test
npm run lint
npm run build
forge lint --approve MAJOR_VERSION_RULE
forge deploy -e development --approve MAJOR_VERSION_RULE
forge storage entities indexes list -e development
```

Repeat the final index-list command until both decision indexes are **ACTIVE**,
then run:

```powershell
forge install --upgrade -e development
```

Scope changes require deployment followed by installation upgrade. Forge's
documentation says new indexes can take at least five minutes to activate.
The npm flag preserves dependency resolution for the existing prerelease UI
Kit scaffold. No Forge login, deploy, install, tunnel, or live Jira write was
run by the coding agent.

## Exactly what to click/check

1. On an existing NC with strong or related-revision matches, open **Apps →
   qualityloop** as an editor. Confirm the saved form still appears. Save it;
   matching must still work. Each eligible card should show its state, history,
   three decision buttons, and the delayed-count wording.
2. Click **Confirm recurrence**. Try a blank reason, then enter a reason and
   optional evidence URLs and click **Record decision**. Check the confirmed
   badge, author display name (or documented unavailable fallback), timestamp,
   reason, and links. Refresh; the state/history must persist.
3. Click **Not a recurrence**. Check that a category is required and the five-URL
   limit is enforced. Record it. Verify the new state and that the earlier
   confirmation is still in history. Click **Correct explanation**, record a
   correction, and verify the state stays the same with another history entry.
4. For a CAPA with effectiveness evidence and an unconfirmed pair, verify
   **Raise effectiveness concern** is disabled and its reason is visible.
   Confirm recurrence first, then raise a concern; also check that absent CAPA
   evidence allows a concern directly. Record the reason. In the second dialog,
   inspect the exact project/title/link listing and choose **Keep decision only**;
   check the recorded concern remains and no task was created.
5. Record a new eligible concern and confirm **Create task and link**. Open the
   task from history: it must be a Task in the CAPA project, with the exact
   `Effectiveness re-review: <CAPA key>` title and a relates-to link to that CAPA.
   Repeated confirmation must not create a second task for that decision.
6. With an NC editor who cannot create in the CAPA project, record a concern.
   Check the exact **Recorded. You can't create tasks in <project>; ask the CAPA
   owner to review.** message. For a test project where Task creation requires
   another field, check that creation reports its separate error and history
   retains the concern. With Link issues denied, check the created task key is
   retained and the linking error is visible.
7. Open the same NC as a browse-only user, including a previously added issue
   panel. Verify saved text, evidence, badges, counts, and history; no capture
   inputs, Save, decision buttons, or E8 button. Verify the exact edit-permission
   notice. Open **QualityLoop evidence** in the issue side section and verify
   the same state/history read-only. Hide a CAPA or an associated NC from this
   user and refresh: no hidden CAPA history/title or hidden-NC count contribution
   may appear. A denied user lookup must not expose an account ID.
8. Open the same pair in two editor sessions. Open decision dialogs before
   either submits. Submit one, then the other. The second must show the other
   decision's current state/history and a conflict notice; it must not append a
   second decision until the engineer explicitly reviews and submits again.
9. For E8, set `E8_CHECK = true`, build, and have the owner deploy. On a fresh
   test pair, click **Concurrency test** on the first strong card.
   Ten rounds must each show 1 success/1 conflict; test totals must be 10/10.
   `pairState.version` must equal total successful writes: the starting version
   plus ten new successes (10 on a fresh pair). Click **Copy results** and paste
   into a text editor. The test leaves ten permanent audit decisions. Its report
   distinguishes prior writes from this test's successes. Disable E8, rebuild,
   deploy, and check the button is absent. No generated sample data is included.
