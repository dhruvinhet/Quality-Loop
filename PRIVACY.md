# QualityLoop privacy

QualityLoop stores quality details (record type, original and normalised part number, failure mode, supplier, line, dates, root cause, actions taken and effectiveness-evidence link) in the `qualityloop` issue property in Jira. Jira controls access to the issue and its properties. Evidence links are stored as links; QualityLoop does not fetch their contents.

Decisions are stored in Forge hosted Custom Entity Store storage. A decision contains the NC and CAPA issue IDs, decision type, the author's Atlassian account ID, reason and reason category where applicable, evidence links, timestamps, and optional follow-up task key, creation claim, opaque recovery token and link completion time. Pair-state records hold the related NC and CAPA IDs, current decision state, version, latest decision ID and update timestamp.

The optional sample scenario stores a `sample:<projectId>` key in the Forge hosted Key-Value Store. It contains the created issue IDs and keys, the creator's account ID, sample definitions and progress needed to create and remove the scenario safely. A sample is created only after confirmation. Its five labelled Jira issues contain illustrative quality data.

Short-lived Forge KVS records hold confirmation plans, removal progress, per-project operation locks and admin maintenance scan tokens. Data health tickets additionally hold record IDs, temporary pagination cursors, counts and pending work; bounded batches hold candidate record IDs. Review records are scoped to the requesting account and expire after an hour. They contain IDs and operation metadata, not copies of Jira summaries or decision narratives. Forge may physically remove expired records later. Operational errors log fixed operation messages only, without exception text, stacks, issue IDs, field values or response bodies.

There is no external network egress, external storage, AI processing or analytics. QualityLoop uses Atlassian-hosted Jira and Forge services. Following an evidence link is a separate action in your browser.

When a Jira issue is deleted, QualityLoop makes a best-effort attempt to remove decisions and pair-state records referring to it. Whole-project cleanup runs when the project is permanently deleted (`avi:jira:deleted:project`), with an 18-second read budget. Projects moved to trash keep their QualityLoop data so it remains available after restoration. QualityLoop does not subscribe to `avi:jira:softdeleted:project`, and the handler ignores any such event already queued. Jira does not send child issue-deleted events for project deletion. Project payloads have no child issue IDs and existing records have no project mapping, so permanent-deletion cleanup scans stored references globally, including legacy records. It can remove eligible older orphaned records from other projects, but protects all projects still in trash.

Jira administrators can use **QualityLoop data → Data health → Check for orphaned records** to scan decisions and pair-state records page by page. This maintenance-only check uses `asApp()` solely to check issue existence, requesting `fields=id` and inspecting HTTP status without parsing or displaying issue bodies. It displays counts and may return app record IDs, never issue titles, quality details or decision narratives. A 404 counts as orphaned only if projects in trash can be excluded; 403, 429, 5xx and transport errors alone never do. **Remove orphaned records** opens a count confirmation. After confirmation, each candidate record, its references and trash safety are freshly checked before deletion. Jira issues are not changed. Trashed-project references and uncertain records are not counted as orphaned and are retained. Review tickets created before this trash-protection policy are rejected and require a new check.

A missing issue's project cannot be reliably identified from the stored issue IDs. QualityLoop therefore retains all missing-issue records whenever any project is in trash or the trash check is unavailable, partial or malformed. The admin check uses the verified Jira administrator's `asUser()` access to search projects with `status=deleted` (Jira's recycle bin), and requires a complete empty result. Project names and response bodies are not returned or logged. Permanent-deletion event cleanup uses the same guard in app context and also requires the app principal's global `ADMINISTER` permission before trusting that project search; otherwise it retains missing references for admin review. The app does not request an additional scope or grant itself that permission. Data is removed after permanent project deletion when these checks succeed, or via confirmed admin Data health removal with the same protection; moving a project to trash does not remove its QualityLoop data.

Admin scans and removal use ten-record pages, a 12-second read budget per invocation and account-bound progress tickets. A browser action handles at most 20 pages before offering resume; a time-budget pause also offers resume. Tickets expire after an hour; reloads or expired/invalid cursors require a new scan. Event delivery delays, eventual storage indexes, permission limits, budget exhaustion or service errors can leave records behind; run another check to retry unresolved or newly indexed records after trash can be excluded. Jira's Get issue API still requires Browse projects and applicable issue-security permissions for the app principal: even an app-context 404 can mean inaccessible rather than physically deleted. Excluding trash does not make a 404 permission-independent proof of deletion. A successful removal followed by an interrupted progress write can under-report the removal count; retry safely re-checks remaining records.

The separate **Scan accessible app records** action remains available to repair older pair-state indexes only when both referenced issues are currently browsable as the acting user, using `asUser()`. Its counts include only accessible records, and it does not remove decisions or change Jira issues. Normal issue-panel evidence and decisions continue to use the viewer's permissions.

**Remove sample scenario** deletes only registered issue IDs that still have the `qualityloop-sample` label and that the acting user can delete. It removes their matching app records and clears the sample registration. Issues that cannot be deleted remain in Jira and are reported; inaccessible issues are not identified. An interrupted create may leave an issue whose ID was never returned to the app; the page warns the user to check the sample label in Jira. Jira removes issue properties with the issue. The admin page never changes quality fields on existing issues.

After uninstall, Atlassian's retention and deletion rules apply to Forge hosted data. Uninstalling does not itself delete existing Jira issues. See [Data lifecycle for Forge-hosted storage](https://developer.atlassian.com/platform/forge/storage-reference/hosted-storage-data-lifecycle/) for Atlassian's current policy, including soft deletion and recovery.
