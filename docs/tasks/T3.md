# T3 developer security self-test

`SEC_TEST` defaults to `false` in `src/config/devFlags.js`. Set it to `true` in
source before building/deploying to show **Security self-test** at the bottom of
the **QualityLoop evidence** `jira:issueContext` view. It is available to users
who can browse the current issue, including users without Edit Issues permission.
It does not appear in the issue-panel capture view. No checks run automatically.
The backend independently refuses the probes and diagnostic modes when the
source flag is false; a frontend payload cannot enable them.

No production permission bug was found. With the flag false, normal resolver
responses, strict payload-field rejection, capture behavior and matching remain
unchanged. No manifest, scopes, dependencies, app ID, storage or triggers changed.
All Jira calls use `asUser()`; all writes target the resolver-context issue only.

## Owner commands

Use Node.js 22.x or 24.x and the existing installed Forge CLI. Enable `SEC_TEST`
in `src/config/devFlags.js`, then run these commands in order from this directory:

```powershell
npm test
npm run lint
npm run build
forge lint
forge deploy
```

Deploy to the intended development environment and existing installation. T3
does not need an installation upgrade because it adds no scopes or modules.
Any future scope change requires owner `forge deploy` followed by
`forge install --upgrade`. Only the owner runs deployment/installation; the agent
did not run either. After collecting results, set `SEC_TEST = false`, then repeat
the commands above to remove the developer UI and disable its backend probes.

## What the checks prove

- **Write attempt:** invokes the existing `saveCapture` resolver with an explicit
  developer marker and a harmless capture payload. The backend first authorises
  the current issue, snapshots its property and reuses its existing editable
  capture fields (or a valid temporary NC if no property exists). It executes the
  real save validation, build and `asUser()` PUT. Browse-only PASS requires exactly
  HTTP 403. Editor PASS requires HTTP 200/201 plus verified restoration. Successful
  writes restore the complete previous JSON, including schema version, original
  part string, timestamp and unknown fields. Originally absent properties are
  deleted and absence checked. Restoration occurs inside the same invocation,
  including after a transport/server failure, independently of frontend lifetime.
  Failed restoration is FAIL, with raw statuses/error; inspect the test issue
  immediately. A forced function timeout cannot guarantee restoration, so use an
  isolated disposable issue and avoid concurrent edits/runs.
- **Payload injection:** calls both `loadCapture` and `findMatches` normally and
  with an extra, different numeric `issueId`, using the explicit developer marker.
  Only in this developer mode is that extra field admitted; it is never used by
  either handler. Production still rejects it. Both handlers use the same resolver
  context and real read/search path. PASS requires both returned source IDs to
  equal the frontend's current issue ID and all returned evidence to match,
  excluding timing/diagnostics. A match candidate's ID can legitimately differ;
  the compared IDs identify the source issue. Denied/missing reads still return
  no record or source ID and fail the check rather than claiming a successful test.
  No payload-ID lookup is needed because that ID is ignored, not accessed.
- **Direct read:** `probeIssueAccess({issueIdOrKey})` authorises that supplied
  identifier with `GET /rest/api/3/issue/{id}?fields=summary` as the current user.
  It returns only `{status, hasSummary}`; no summary text, issue body, title or
  count is returned. For a known restricted issue, PASS requires 403/404 and
  `hasSummary: false`. A typo/missing issue can also return 404, so independently
  confirm that the target exists using an authorised account.
- **JQL escaping:** `probeJqlEscaping` sends three enhanced JQL searches using
  the actual `buildMatchJql` and its existing `escapeJqlValue`, with bases
  `SEC"QUOTE`, `SEC\BACKSLASH` and `SEC'APOSTROPHE`. Each fixture gets a PASS/FAIL
  and its raw status/error; all must return 200. Returned search data is discarded.
  Zero matches is fine. HTTP 400 is FAIL, not a successful no-match result.

Results include a UTC run timestamp, expected permission, source IDs and raw HTTP
statuses/errors. **Copy results** uses the existing Forge-hosted Frame to copy
plain text. Browser denial offers selected text for manual copying. The report
contains diagnostics, not capture content or match summaries. Copying is available
after completion; later runs replace the report. Checks run sequentially and the
write runs last to avoid comparing reads across its own transient index update.

## Exact live click/check sequence

1. As an editor, prepare an isolated test NC: open **qualityloop** in the issue's
   Apps menu, save part `SEC-100-A`, failure **FM-01 Crack**, and detected date
   `2026-10-31`. Record the saved fields and current numeric issue ID. Prepare
   another issue with a different numeric ID, plus an existing issue hidden from
   the test user by project permissions or issue security. Let indexing settle.
2. As a browse-only user, open that NC and expand **QualityLoop evidence** in the
   right-hand issue-context area. Check **Security self-test** appears at its bottom,
   including when there is no matching CAPA. Check it is absent from **qualityloop**.
3. Enter the other numeric ID and the known restricted ID/key. Leave the permission
   selector at **Browse-only user: expect 403**, then click **Run security self-test**.
   Check both injection rows PASS with both returned source IDs equal to the current
   ID, direct read PASS with 403/404 and false, each JQL fixture PASS with 200, and
   write PASS with `save PUT` 403. Refused writes must never show a successful save.
4. Click **Copy results**, paste into a text editor and verify the UTC timestamp,
   expectations, source IDs and all PASS/FAIL/status/error rows. If clipboard access
   is blocked, use the selected plain-text fallback. Confirm no restricted summary
   text or capture/match content is present.
5. Repeat as an editor, selecting **Editor: expect successful write and restoration**.
   Use an issue restricted from that editor for the direct-read check too. Expect
   `save PUT` 200/201, `restore PUT` 200, `restore GET` 200 and `restored: true`.
   Reopen **qualityloop** and confirm every saved field is unchanged. To check the
   exact JSON/timestamp, use an authorised Jira property GET before and after.
6. Optionally repeat on an isolated issue without a capture: injection correctly
   fails with no source data; editor write creates then deletes the temporary
   property (`restore DELETE` 204, `restore GET` 404). Also enter a browsable target
   in the restricted-issue box: direct read should FAIL with 200/true, without
   displaying summary text. This verifies the test distinguishes allowed access.
7. Disable `SEC_TEST`, build/deploy again, reopen both issue views and confirm the
   section is absent. Automated tests prove that the disabled backend also refuses
   probe invocations and developer diagnostic payloads without making Jira calls.

## Verification and documentation limits

98 Jest tests, ESLint and the build pass locally. Tests cover both default-disabled
and deliberately enabled backend paths, context authority, safe direct responses,
real JQL construction, write refusal, exact restoration, absent-property cleanup,
transport errors, result verdicts, sequencing and plain-text output. Test discovery
is limited to `src/`; `eval/test/` was not accessed. Forge CLI is unavailable
locally, so `forge lint` remains an owner command. Live rendering, actual site
permissions, Jira JQL parsing, timeout behavior and browser copying remain live
owner checks; no live pass is claimed.

Forge MCP verified the backend/UI Kit guides, component props, Frame/Events and
clipboard policy, plus exact REST operations and scopes for issue GET, property
GET/PUT/DELETE and enhanced-search POST. Existing scopes `read:jira-work` and
`write:jira-work` cover all calls. MCP search did not return an authoritative JQL
literal-escaping reference (it returned Jira expressions/CQL); the existing escape
function was not changed. The live 200 checks explicitly test that remaining gap.
