## Count and history coverage

Counts discover pair-state records through the existing `by-capa` index, never raw CONFIRM events. Query up to **51 pairs**, reauthorize each distinct referenced NC asUser, then directly read its current pair state. Repeated CONFIRMs on one NC therefore count once. No date-since-closure filter applies to the new current-confirmation meaning.

Display `50+` only after verifying **51 browsable, currently confirmed NCs**. Simply finding more than 50 stored pairs cannot safely justify `50+`: some may be hidden or no longer confirmed. If the bounded pair scan has more pages, or a legacy confirmation cannot be resolved within its bound, display the verified lower bound with “limited check; total unavailable”. Hidden records cannot inflate that value. Preserve the “may take a few seconds” note for index lag.

Discover at most 50 historical pairs for the current issue, in addition to current strong/revision cards. History queries use the existing decision `by-issue` index, descending creation date, and a CAPA filter, collecting at most 51 records to display the newest 50. Read the committed latest decision directly to fill an index-lag gap. Show “Older decisions not shown” for a continuation/cap. In-memory filters can yield empty pages; every storage query stops after at most 10 pages and discloses continuation. Legacy confirmation reads collect at most 100 history events; if the decisive event remains outside that bounded history, treat confirmation as unknown, not false, and refuse a preserving write rather than guessing. These limits also share the overall load deadline.

## Jira/Forge documentation verification

Verified through the Forge MCP: backend, manifest, development and UI Kit guides; module/component inventories and component references; enhanced POST search and issue GET operation schemas/scopes; custom entity boolean attributes and bounded descending/filter/cursor queries. The REAL script's create issue (including inline issue properties), delete issue, and project issue-type metadata endpoints/scopes were also checked.

The [enhanced search API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-search/#api-rest-api-3-search-jql-post) documents `properties` as up to five requested issue properties, returned as the issue's `properties` map. It **does not guarantee those values are current**. Its operation description explicitly warns that recent updates may not be immediately visible; [search and reconcile](https://developer.atlassian.com/cloud/jira/platform/search-and-reconcile/) describes stronger read-after-write behavior with `reconcileIssues` (maximum 50 known IDs). Accordingly, search values are classification snapshots; every returned card is directly re-read asUser and must retain its classification. This cannot recover a candidate omitted by a stale search index; refresh after indexing catches up. No freshness guarantee beyond the documented contract is claimed.

The existing `read:jira-work`, `write:jira-work`, `read:jira-user`, and `storage:app` scopes remain unchanged. [Custom entity attributes](https://developer.atlassian.com/platform/forge/storage-reference/entities-manifest/) support boolean additions, and [entity queries](https://developer.atlassian.com/platform/forge/storage-reference/entities-api-query/) document Sort.DESC, in-memory filters, cursors and a maximum page size of 100.

Unverified here: actual Jira property/index latency, real network performance, deployed Forge UI/runtime behavior, and live install/storage-schema rollout. Forge CLI was absent on PATH and locally, so `forge lint` was unavailable. Runs on Atlassian eligibility was not independently certified.
