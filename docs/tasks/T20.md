# T20 — Wording polish from live check

Implemented the requested follow-up wording, link verification wording, and retention of freshly reclassified signature candidates. The deterministic matching rules and Jira write behavior are unchanged. The only behavior correction is routing a directly re-read signature candidate to its current class instead of dropping it. No manifest or scope changes. The hidden `eval/test/` split was not opened or modified.

## Files changed and why

- `src/lib/decisions.js`: replace the technical new-task marker sentence with **Add a hidden QualityLoop marker to the new task so it can be identified later.** The task summary, CAPA link text, intended assignee, unassigned text, and assignee rejection fallback remain unchanged.
- `src/lib/followup.js`: start the link confirmation with **Check that {taskKey} is linked to the CAPA; add a Relates link only if it is missing.** Keep the actual CAPA key and link-completion recording explicit in the following sentences. Preserve the conditional marker-write disclosure and legacy warning.
- `src/frontend/DecisionDetails.jsx`: label a saved task with unrecorded link completion **Verify link**. Use **Confirm link verification** and **Confirm verification** in its dialog, and name the current button in the interrupted-response message. Existing resolver names, permission checks, and separate confirmation action are unchanged.
- `src/resolvers/decisions.js`: update retry messages to refer to **Verify link**. No resolver control flow or Jira/storage writes changed: confirmed requests still re-authorise, check the existing link, create it only if missing, and record completion.
- `src/resolvers/evidence.js`: classify each completed direct read against both allowed signature classes. Retain a strong-to-related-revision or related-revision-to-strong move in its fresh class. Keep at most 25 cards per signature class, ordered by closure descending and key ascending; if a late move enters a full class, retain the newest verified 25. Exclude displaced cards from historical-pair loading. Preserve the five-read concurrency bound, refill loop, shared budget, permission handling, search caps, and unchecked-snapshot counts. Other-related queries retain their existing classification boundary.
- `src/lib/__tests__/decisions.test.js`: update exact creation confirmations; add a regression for the friendly marker sentence and absence of technical schema names.
- `src/lib/__tests__/followup.test.js`: update the expected verification wording.
- `src/frontend/__tests__/evidenceLoading.test.js`: update dialog/button assertions; add a legacy history regression with a saved task key and no completion flag. Keep the separate confirmation and read-only assertions.
- `src/resolvers/__tests__/decisions.test.js`: update creation/verification wording; add legacy verification cases with an existing and a missing link. Repeated confirmations create zero or one links respectively and never add a marker to a legacy task.
- `src/resolvers/__tests__/scale.simulated.test.js`: replace the old drop-on-reclassification expectation with both-direction retention and decision availability. Add both-direction overflow cases for newest-25 retention, no duplicate reads, cache/displaced-card handling, and unchanged unchecked-candidate semantics. Add a regression that a signature candidate moving outside both signature classes is still excluded.
- `docs/tasks/T20.md`: record this change, validation, limitations, and owner checks.

3. Open the read-only side view: link verification must remain disabled. A new task whose earlier link write failed uses the same **Verify link** entry point and existing conditional marker-write disclosure.

If Jira search returns an older classification while the direct read sees a changed revision, check that the card appears in its current class. This race is timing-dependent in live Jira; `npm test` deterministically verifies both directions, full destination classes, fresh ordering, and decision availability on moved cards.
