# T24 — QL-004: spaces around hyphens are removed

Read `AGENTS.md`, review §1.3 and QL-004 before implementation. T23 remains in
place. Only T24 is implemented; no later review task is included.

## Files changed and why

- `src/lib/normalise.js`: adds the named part-number rule **spaces around hyphens
  are removed** using `.replace(/\s*-\s*/g, '-')` after the existing
  trim/whitespace-collapse/uppercase steps. It runs before revision extraction.
  `partOriginal` remains untouched. `normaliseText` is unchanged, so failure modes
  do not acquire the new part-specific rule. This is deterministic formatting
  normalisation, not fuzzy matching or typo correction.
- `src/lib/__tests__/normalise.test.js`: covers all four requested SM-6604 variants,
  tabs/newlines on either side of hyphens, original preservation, idempotence,
  unchanged failure-mode text rules, and retaining actual hyphens and typos.
- `src/lib/__tests__/match.test.js`: covers strong matches for all four requested
  variants with deliberately stale stored `partNorm`/`partBase`, re-normalising a
  legacy NC, different revisions staying related, typos excluded from matching,
  unchanged failure-mode rules, and JQL's stored-index limitation. Uses frozen
  input objects to verify matching does not migrate or mutate stored records.
- `src/lib/__tests__/hints.test.js`: changes the spaced-hyphen case from hint-only
  to strong and verifies it is absent from hints. The transposition case remains
  hint-only, with original strings preserved.
- `src/frontend/__tests__/hintResults.test.js`: replaces the obsolete formatting-only
  hint fixture with a true transposition (`SM-6640 -A` versus `SM-6604-A`). Existing
  rendering, cautious copy, collapsed state, and no-decision-control checks remain.
- `src/lib/__tests__/capture.test.js` and `src/resolvers/__tests__/index.test.js`:
  update stored normalised-part/base expectations while retaining original input
  strings and T23's validation/type-lock coverage.
- `eval/reference/score.js`: independently implements the updated written rule in
  a part-specific `normPart`, without importing application code. Failure-mode
  reference normalisation, date rules, frozen-file checks and labels are unchanged.
- `eval/README.md`: updates the written L1 rules explicitly, distinguishing part
  normalisation from failure-mode text normalisation.
- `eval/DISPUTES.md`: records that this changes the written rule after freeze,
  explains NC-027/CAPA-15 moving from hint to strong, confirms frozen data was not
  touched, and records the measured score changes.
- `README.md`: documents the named rule, updates current dev metrics and records
  the legacy stored-field/JQL limitation and owner repair action.
- `docs/tasks/T24.md`: records implementation, validation and owner handoff.

## Legacy records and the JQL limitation

`matchCaptures` already re-normalises both `current.partOriginal` and
`candidate.partOriginal` in memory. No production matcher rewrite was needed;
the new regression tests prove stale derived fields are ignored once records are
fetched. Different revisions still remain related, never strong.

**Yes: `qlPartBase` JQL can still miss existing CAPAs stored with a trailing-space
base**, such as `SM-6604 `, when searching for `SM-6604`. Existing stored fields
are not automatically migrated. This task does not expand the query or add a
background repair. In-memory normalisation cannot recover candidates the search
does not return, and a formatting-only candidate is no longer a hint simply
because its stored base is stale. Open and re-save each affected CAPA to refresh
`partNorm`/`partBase`; wait for Jira property indexing before refreshing the NC.
T23 requires a closed date on that save, including repairs to legacy CAPAs.

## Exactly what to click and check

1. Open a fresh Jira issue → **QualityLoop** → **Set up as CAPA**. Enter
   `SM-6604 -A`, select a failure mode, enter a valid closed date, then **Save**.
   Confirm the form retains the original part string and record type locks.
2. Open another fresh issue → **QualityLoop** → **Set up as NC**. Enter
   `SM-6604-A`, the same failure mode and a detected date one day after the CAPA's
   closed date. Click **Save**, then **Refresh evidence and decisions** after
   indexing. Confirm a strong/possible-recurrence card, with the CAPA's original
   `SM-6604 -A` still displayed and no formatting-only hint for that CAPA.
3. On the CAPA, repeat saves with `SM-6604- A`, ` SM-6604 - A ` and clean
   `SM-6604-A`. Refresh the NC after each indexing update: each stays strong.
4. Change that CAPA's part to `SM-6604 - B`, save and refresh the NC. Confirm it
   appears only as a related revision. Change it to the typo `SM-6640 -A`, save
   and refresh: it must not be strong or related-revision; it may appear as a
   labelled hint within the existing hint-search cap.
5. If a legacy CAPA already has the trailing-space stored base, observe that it
   can be absent from NC results before repair. Open that CAPA's panel, supply a
   closed date if necessary, click **Save**, wait for indexing, then refresh the
   NC. Confirm it now matches without rewriting the original part string.
6. Recheck T23: blank CAPA closed date rejects Save, a saved record's type stays
   disabled, and a CAPA closed on the NC detection date is still excluded.
