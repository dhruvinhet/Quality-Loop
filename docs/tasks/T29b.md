# T29b — editable inactive codes and compact catalogue rows

Read AGENTS.md and T29.md first. This note supersedes T29's requirement to
choose an active code when editing an existing inactive-code record. Earlier
task/review records remain unchanged, as do review §1.3 and T23–T29 protections.

## Changes and files

- `src/lib/capture.js`, `src/resolvers/index.js`: validation accepts an active
  code or the canonical code already stored on this issue. The server passes
  the failure mode from the property it already reads asUser, never from a
  frontend-supplied exception. New records with inactive codes and changes to
  another inactive code remain rejected; switches to active codes succeed.
  Valid stored codes absent from the catalogue can also be retained. Empty or
  malformed codes do not obtain the stored-code exception. All other capture
  checks, record-type lock and Jira permission behavior remain unchanged.
- `src/lib/failureModes.js`: one label helper retains labels for inactive modes
  (`FM-08 Wire fracture (inactive)`). Only a code absent from an available
  catalogue gets `FM-08 (not in catalogue)`. An unavailable lookup displays the
  code alone rather than asserting absence. A shared non-mutating code sort is
  used for seed/catalogue results and dropdowns. Options contain active codes
  plus this record's stored code, with its correct label/status.
- `src/frontend/CaptureForm.jsx`: keeps the stored inactive/absent code selected
  and present in the sorted dropdown. Client validation uses the same stored-code
  exception as the server. Removes the instruction blocking an ordinary edit.
- `src/resolvers/failureModes.js`: returns stored catalogues sorted by code;
  existing revision/lock/admin checks are retained. Label/mode edits also persist
  the sorted catalogue through the shared helper.
- `src/frontend/FailureModeCatalogue.jsx`: one Inline row per code with separate
  code/label text, Active/Inactive Lozenge and adjacent compact Rename and
  Deactivate/Activate buttons. ButtonGroup has an accessible code-specific label.
  Rows can wrap on narrow views while the action buttons stay grouped. Existing
  uncontrolled edit inputs, permission errors and duplicate-action guard remain.
- `src/frontend/EvidenceResults.jsx`: removes the persistent supplier migration
  banner from the NC panel. Search/matching logic and completeness checks remain.
- `src/frontend/adminPage.jsx`: adds the short supplier migration note under
  App data maintenance. `README.md` retains the full JQL limitation and updates
  the inactive-edit/label/sorting behavior.
- `src/frontend/MatchView.jsx`: distinguishes an unavailable catalogue from an
  available empty catalogue, preserving the existing lookup warning and avoiding
  false “not in catalogue” labels during a lookup failure.
- `src/lib/sampleScenario.js`, `src/resolvers/samples.js`: sample preview lines
  take the current site catalogue, including renamed/inactive labels. Prepare
  reads it once after the existing project/creation-metadata checks. Codes,
  sample captures and confirmed Jira writes are unchanged. Cards, hints and
  read-only details already share the label helper and inherit its correction.
- Tests: `src/lib/__tests__/failureModes.test.js`, `sampleScenario.test.js`;
  `src/resolvers/__tests__/index.test.js`, `samples.test.js`;
  `src/frontend/__tests__/captureForm.test.js`, `evidenceLoading.test.js`,
  `dataHealth.test.js`, `hintResults.test.js`, `failureModeCatalogue.test.js`.
  Cover all four requested save cases, canonical comparisons, rejection of a
  payload-supplied exception, absent-code retention, inactive/absent labels in
  each rendering path and real sample preparation, non-mutating code sorting,
  the selected stored option, compact rows/lozenges/grouped actions, banner
  removal and admin-note placement.
- `docs/tasks/T29b.md`: this new implementation and owner handoff record.
