## Follow-up recovery constraints

Recovery searches enhanced `POST /rest/api/3/search/jql` as the viewer, capped at 200 candidate issues, ten pages and a 15-second search budget. It verifies candidates directly in batches of five. Zero matches explain visibility/indexing limitations; multiple matches or an incomplete search require manual inspection. Exactly one verified result opens the recording confirmation. Confirming repeats the search and authorization and conditionally stores the task key. Recovery never calls task creation or creates a missing Jira link.

T14 task claims have only a random UUID, with no claim timestamp. That time cannot be reconstructed reliably from the decision's earlier creation time. Their **Check for task** action explains that the claim time was not recorded and requires manual Jira inspection; it does not guess or create another task. New T15 claims support timestamp-based recovery.

Creation can still be rejected if the project's configuration disallows unassigned tasks or requires additional fields. Such a failure preserves the concern and claim and reports the separate creation error. Jira automation can change ownership; the success message uses the actual viewing-user read after creation.

## SIMULATED load results

The new simulation exercises the real resolver and store code against in-memory Jira and custom entities: one visible NC, three CAPAs, five decisions per pair, one shared author, and three legacy pair states. Histories are complete and there are no task-key reads or network delays. The same fixture was run before and after the implementation. Counts exclude the separately invoked hint resolver.

| Calls per unified load | T14 initial/repeat | T15 initial | T15 repeat |
|---|---:|---:|---:|
| Jira | 8 | 8 | 8 |
| Storage direct GET | 6 | 3 | 3 |
| Storage query | 10 | 7 | 7 |
| Storage transaction | 0 | 3 | 0 |
| Total storage operations | 16 | 13 | 10 |

Storage reads fall **16 → 10**; the first load adds three one-time backfill transactions. The repeat has **37.5% fewer storage operations**. The simulation asserts these counts and separately verifies five concurrent CAPA loads and a single shared in-flight NC read. This is not a measured improvement to live 10–15-second latency.

The existing 500/1,000-CAPA scale fixture falls from **248 to 98 Jira calls** per unified load because only 25 strong + 25 revision + 40 other-related cards are directly fetched. Its signature search still checks up to 200 candidates. Other-related limits remain unchanged. The 0/100-CAPA cases remain 5/85 calls.

## Forge documentation and limitations

Consulted the Forge MCP development, backend, UI Kit, manifest and module guides, enhanced search and issue read/create operation schemas and their required scopes, custom entity attribute definitions and conditional transaction documentation. Create issue requires the already-declared `write:jira-work`; issue reads/search require `read:jira-work`. Assignment does not require a scope addition. The existing user lookup and permission checks remain unchanged.

Cross-module custom emission in the [events documentation](https://developer.atlassian.com/platform/forge/custom-ui-bridge/events/) is described for Custom UI. Jira's [issue-context events](https://developer.atlassian.com/platform/forge/manifest-reference/modules/jira-issue-context/) document Jira issue updates/comments, not a custom-storage decision notification. [view.refresh](https://developer.atlassian.com/platform/forge/apis-reference/ui-api-bridge/view/) documents a parent-page data refresh, without establishing that another UI Kit module reloads custom-storage data. No explicit UI Kit cross-module contract was established through the Forge MCP. Per T15's fallback, automatic side-view refresh is unchanged; click **Refresh evidence and decisions** in the side view.

Not verified: live assignment/unassigned configuration and automation, live recovery/indexing and exact recovery JQL execution, real latency, deployed Forge UI/packaging, and the new storage-attribute rollout. Forge MCP searches for the new summary/date JQL details returned CQL material rather than a matching Jira field reference, so that detail was not independently documented through the available index. The enhanced-search endpoint/body/scopes were verified. No alternative API shapes or scopes were invented. Forge lint could not be run: no offline Forge CLI was found on PATH or in `node_modules/.bin`.
