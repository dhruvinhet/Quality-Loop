## Files changed and why

- `src/resolvers/searchSettings.js`: the shared permission helper requests
  `/rest/api/3/mypermissions?projectId=<id>&permissions=ADMINISTER_PROJECTS,ADMINISTER`
  asUser. It permits either flag only when havePermission is strictly true.
  The getter's canAdmin and both save gates use that helper. The second check
  still happens immediately before writing settings; losing both grants blocks
  the write and releases the lock. Existing browse/context/target-project checks,
  edit revision and lock ownership are unchanged.
- `src/lib/searchSettings.js`: shared exact permission message:
  “Administer Projects on this project or Jira administrator permission is
  required to change these settings.”
- `src/frontend/ProjectSearchSettings.jsx`: displays that same message for a
  browse-only viewer. A Jira-admin-only user now receives canAdmin from the
  resolver and sees the existing form.
- `src/frontend/projectPage.jsx`: walkthrough first, then a Sample scenario
  heading with existing controls, sample links, readiness/status/confirmation
  handling, then ProjectSearchSettings last. The guided ready-NC link remains
  in walkthrough step 2. Sample writes and confirmations are unchanged.
- `src/resolvers/__tests__/searchSettings.test.js`: project-admin-only,
  Jira-admin-only, both and neither cases cover canAdmin and save. Every helper
  call must use the combined comma-separated query in the contextual project.
  Separate revocation tests cover each grant being lost before the second gate.
  Existing unrelated-project, denied-context, stale/locked settings and privacy
  tests remain.
- `src/frontend/__tests__/projectSearchSettings.test.js`: exact updated read-only
  permission message.
- `src/frontend/__tests__/projectPage.test.js`: asserts walkthrough → Sample
  scenario heading → all sample controls/readiness/list links → settings last.
- `README.md`: correct permission alternatives and page ordering.
- `docs/tasks/T30b.md`: this new record and owner handoff.
