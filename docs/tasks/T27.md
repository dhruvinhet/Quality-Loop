## Files changed and resulting behavior

- `src/lib/followup.js`: builds the verified ADF description using doc/version 1,
  paragraph/text nodes and link marks. It contains the decision label, linked NC
  key + summary, CAPA key, engineer reason/category when present, only evidence
  URLs accepted by `validEvidenceUrl()`, and the exact full-history instruction.
  The NC browse URL uses the authorised issue's `self` origin; account/author
  objects are not copied into the description. Adds a plain description preview,
  conservative empty-description detection and expanded repair confirmation.
- `src/lib/decisions.js`: creation confirmation names the selected issue type,
  description preview, both Relates links (or explicitly unlinked creation),
  marker, storage recording, assignee and approved validation fallbacks. The same
  function generates the proposal and the string checked before creation.
- `src/resolvers/decisions.js`: resolves project-specific creation metadata before
  confirmation, preferring Task even on a later page, otherwise the first standard
  non-subtask type. A missing Relates type no longer blocks follow-up creation;
  the dialog explains unlinked creation and Verify later. No standard type, or
  incomplete metadata, blocks creation before a claim.
  Creation includes ADF and the opaque marker. It persists `taskKey` before
  optional completion work. Description-only validation rejection can retry
  without description under the same durable claim; assignee rejection can retry
  unassigned as before. At most three attempts cover those two definitive field
  rejections. Other 400 errors, denial, transport errors, 429 and 5xx never cause
  an automatic create retry.
  The task, CAPA and NC are freshly read asUser before each marker, description
  or link write. Create attempts freshly read both source issues. Changed
  description/assignee/plan confirmations are rejected. Loss of source visibility
  returns nothing, even between the two link writes.
  Both create and Verify check both Relates links and add only missing ones.
  Verify fills only an empty description and preserves nonempty owner notes.
  Description/link failures return a clear **created with limits** result (or
  **remains with limits** during repair) with the stored key. Missing links and
  empty descriptions can be repaired later without creating another issue.
  Legacy marker rules, wrong-marker refusal and lost-create recovery remain.
- `src/resolvers/decisionStore.js`: independently records description, CAPA-link
  and NC-link completion. Each conditional transaction checks the claim/key and
  observed other timestamps, preserving concurrent progress and newer metadata.
  Lost transaction responses are reconciled by direct reads; competing completion
  writes merge with bounded retries.
- `manifest.yml`: adds two optional string attributes to `decision`:

  | Attribute | Meaning |
  | --- | --- |
  | `taskLinkedAt` (existing) | CAPA Relates link completion |
  | `taskNcLinkedAt` (new) | NC Relates link completion |
  | `taskDescriptionAt` (new) | Description present/verified |

  History reports completion only when all three exist. An old CAPA-only stamp
  cannot imply NC completion. Old records need no destructive migration; they
  offer Verify link until the additional checks finish.
- `src/frontend/DecisionDetails.jsx`: uses **Create follow-up**, so a confirmed
  unlinked creation does not have a button promising links. T25b's input handling
  and T26's counts are unchanged.
- `src/lib/__tests__/followup.test.js`, `src/lib/__tests__/decisions.test.js`:
  exact ADF/link shape, reason/category/history instruction, credential/HTTP
  filtering, absence of account IDs, confirmation strings, fallback/unlinked
  wording and preservation of existing rich descriptions.
- `src/resolvers/__tests__/decisions.test.js`: description correctness and two
  link calls; fresh authorization before writes; Story fallback and later-page
  Task preference; missing Relates; description rejection and later repair;
  partial NC-link denial/transport failure; lost access between links; repeated
  two-link repair; legacy completion flags; unrelated validation failures.
  Existing claim, assignee fallback, ambiguity/no-retry, recovery and opaque
  marker tests still pass. Fixtures now model the description and both Jira links.
- `src/resolvers/__tests__/decisionStore.test.js`: additional conditions and a
  simultaneous three-way completion merge test, retaining claim/key and
  lost-response checks.
- `README.md`: updates follow-up behavior and fallback/repair policy.
- `docs/JUDGE-INSTRUCTIONS.md`: supported classic/company-managed Task + Relates
  demo and follow-up inspection/repair instructions, plus fallback limitations.
- `docs/tasks/T27.md`: implementation, documentation verification and handoff.

## Exactly what to click/check live

1. In the supported Task + Relates demo project, open the DEMO new NC and save
   quality details. On eligible CAPA-B, record **Effectiveness concern** with a
   complete reason and valid HTTPS evidence. Review the follow-up dialog: Task
   (or the actual fallback name), full description preview, NC/CAPA links,
   marker and assignee/fallback. Click **Create follow-up**.
2. Open the created issue from history. Check the decision label, linked NC key
   and summary, CAPA key, reason/category if present, clickable HTTPS evidence and
   **Open the QualityLoop panel on <NC key> to see the full history.** Check that
   its Relates links include **both** NC and CAPA. No account IDs should appear
   in the generated description.
3. On a test project with only Story as a standard type, confirm that the dialog
   names Story and creation uses it. If required custom fields block it, confirm
   the clear error and that another issue is not automatically created.
4. Where Relates is unavailable, review the explicit unlinked-creation warning.
   Create once: confirm **created with limits** and a retained task key. After a
   Jira admin enables Relates, use **Verify link**, review/confirm both links and
   any empty-description repair. Repeating verification must not duplicate an
   issue or link. Use controlled test configuration, not a production link-type
   change; mocked tests cover this if the demo site cannot reproduce it safely.
5. Use Verify on an older CAPA-only task: it should retain the existing link and
   add the missing NC link. Empty descriptions are filled; nonempty owner notes
   remain intact. Partial description/link failure must retain the same task key
   and offer repair. Permission loss must not expose inaccessible issue data.
6. Recheck assignee rejection/unassigned fallback where available, and the prior
   T23–T26 capture protections, typing/paste, URL messages, hints and count copy.
   Review on GitHub and test live before starting the next prompt.
