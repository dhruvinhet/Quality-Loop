# T22 / T22b — QL-08 / N-04 orphan cleanup and project-trash protection

T22b corrects the original T22 policy: **trashed projects keep their QualityLoop data**. Whole-project cleanup runs only after permanent deletion, or through confirmed admin Data health removal with trash protection. Individual issue-deletion and sample-removal cleanup retain their existing behavior. Read AGENTS.md before this task; eval/test/ was not opened or modified.

## Current project-event behavior

Forge documents these project events:

| Event | Meaning |
| --- | --- |
| `avi:jira:created:project` | Project created |
| `avi:jira:updated:project` | Project updated |
| `avi:jira:softdeleted:project` | Project moved to trash |
| `avi:jira:deleted:project` | Project permanently deleted |
| `avi:jira:archived:project` | Project archived |
| `avi:jira:unarchived:project` | Project unarchived |
| `avi:jira:restored:project` | Project restored |

The project events require classic `read:jira-work`, or granular `read:project:jira` as an alternative. Payloads include `eventType`, `selfGenerated` and project metadata including its ID, but no child issue IDs. The existing trigger still handles issue deletion and permanent project deletion through `index.onIssueDeleted`. Delivery can take up to three minutes; project deletion does not emit child issue-deleted events. Sources: [Jira events](https://developer.atlassian.com/platform/forge/events-reference/jira/) and [cascading events](https://developer.atlassian.com/platform/forge/events/), verified through Forge MCP in T22.

**The soft-delete subscription is removed. The handler also ignores queued soft-delete events without reading storage or Jira, or deleting anything.** Permanent deletion retains the existing bounded, 18-second global reference scan over both record entities, including legacy pairs. Its candidates now pass the same trash guard as Data health, preventing deletion of another project's restorable data. Without project mappings, the scan can also remove eligible pre-existing orphans from other projects.

## Trash protection and conservative fallback

A missing issue's 404 response does not identify its project, and current stored records do not contain a reliable current project association. Jira documents `GET /rest/api/3/project/search?status=deleted` as searching projects in the recycle bin; the status parameter is marked experimental. The endpoint returns projects visible to the calling principal. A principal with global `ADMINISTER` has the visibility required for the complete trash check.

For each candidate 404, QualityLoop requests `status=deleted&startAt=0&maxResults=1` and trusts **only** a successful, complete empty result: `startAt: 0`, `total: 0`, `isLast: true`, an empty `values` array and no next-page URL. Any project in trash, partial/malformed response, denial or error prevents counting/removal of that missing-issue record. This deliberately retains all missing-issue records while any project is in trash, including unrelated permanently deleted issues. No historical project mapping or inference from an issue key is used.

Admin resolvers verify Jira `ADMINISTER` permission asUser on every invocation and use that administrator's asUser access for the project-trash search. Issue existence still uses asApp with `fields=id`, inspecting only status and never parsing an issue body. Project metadata is not returned or logged. In permanent-event context there is no acting admin user, so the app verifies its own global `ADMINISTER` permission before trusting an asApp project-trash search. If it lacks that permission, cleanup retains missing references for admin review. No scope or admin permission is granted to the app by this change.

Data health result text says: **Trashed projects keep their QualityLoop data. Missing-issue records are not counted as orphaned if any project is in trash or the trash check is unavailable.** Uncertain records contribute to the unresolved count, never the orphan count. Confirmed removal repeats both the issue checks and trash guard. Tickets created under the previous policy are rejected and require a new check, preventing old candidate counts from bypassing protection.

A record is removable only with two valid issue references, a fresh explicit issue 404 and successful trash exclusion. Two 200s mean live; malformed references and denial/error alone are unresolved. The Jira issue API still defines 404 as missing or inaccessible, so excluding trash does not make 404 permission-independent proof of physical deletion.

Read the Forge manifest, backend and UI Kit guides and Text component reference. References: [projects API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-projects/#api-rest-api-3-project-search-get) and [permissions API](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-permissions/#api-rest-api-3-mypermissions-get). No newly used API or manifest shape remains unverified. The exact 60-day restore window was supplied in the task; Forge MCP confirms recycle-bin restoration but did not independently establish that duration. No behavior depends on a fixed number of days: projects still in trash are protected regardless of age. Live event delivery, project-search visibility, Jira rendering and permission behavior remain untested; unit tests simulate them. No app-global admin permission is assumed or requested; permanent event cleanup may defer to the acting Jira admin's Data health check.

Storage queries are eventually consistent and cursors can expire. Re-run a check for records missing from a query snapshot or after trash becomes safely excludable. Reloading loses the frontend ticket; a new check is safe. Old-policy tickets, expired tickets and invalid cursors require a new scan. A failed request can leave a per-ticket lock until TTL cleanup. Interrupted progress persistence after a successful deletion can under-report the removal count; retries re-check remaining records and never recreate deleted data.

1. In a disposable development project, record an NC/CAPA decision and note its state/history. Move the project to Jira **Trash**. Check that the app trigger no longer subscribes to soft deletion and that the records remain. Restore the project and reopen the NC's **QualityLoop** panel; click **Refresh evidence and decisions** and verify the earlier decisions/state remain.
2. With that project in trash, sign in as Jira admin and open **Jira settings → Apps → QualityLoop data → Data health**. Click **Check for orphaned records**. Its missing-issue records must not increase the orphan count; they are retained/unresolved, and the new result text explains the conservative trash policy. Unrelated missing-issue records are also held while any project is in trash.
3. If a scan pauses, click **Resume orphan check**. Counts stay cumulative. Old-policy tickets should ask for a new check rather than reuse old candidate counts.
4. After permanent deletion of the disposable project, the existing bounded event scan still runs. It removes eligible 404 references only when the app can establish full empty-trash visibility; otherwise it defers safely. As Jira admin, run Data health after no projects remain in trash to check retained candidates.
5. Where candidates are found, click **Remove orphaned records**. Verify the count dialog mentions the issue recheck and ruling out projects in trash. Click **Cancel** and verify no removal. Reopen and click **Confirm removal**; check removed/retained counts. If any project has moved to trash since the scan, references must be retained. That race is tested deterministically.
6. Keep existing checks for 403/500 retention, denied non-admin calls, budget/pagination resume, accessible-only index repair and unchanged dev eval numbers. No maintenance action should change a Jira issue.
