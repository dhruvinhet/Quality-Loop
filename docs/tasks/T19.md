## Files changed and behavior

- `src/lib/followup.js`: define the `qualityloop-followup` marker `{ schemaVersion: 1, decisionId, capaId, ncId, claimedAt }`, conservative marker verification, legacy warning, link detection in either direction, and explicit repair confirmation text. A present conflicting/malformed marker never falls back to legacy recovery. Marked recovery also checks NC ID and claim time, in addition to the required decision and CAPA IDs.
- `src/lib/decisions.js`: include the new task's marker-property write and its fields in the existing follow-up confirmation, retaining assignee/rejection wording.
- `src/resolvers/decisionStore.js`: new durable claims record `taskMarkerVersion: 1` before Jira creation. Missing version denotes a pre-T19 claim. Save the task key independently of link success; record `taskLinkedAt` with a separate transaction conditioned on the same claim and task key. Reconcile ambiguous storage responses by direct reads and preserve current metadata. Tighten same-key reconciliation so a different claim cannot be treated as success.
- `src/resolvers/decisions.js`: after creating a task, save its key, re-authorise the task as the user, write the marker on the task, create its Relates link, then record link completion. Marker or link failure leaves the known task key available for repair. Recovery re-reads candidates with the marker as the viewer, accepts matching markers, and permits unmarked tasks only for legacy claims. It preserves bounded search, completed-search uniqueness, explicit confirmation, repeated authorisation/marker verification, and the prohibition on automatic replacement creation.
- `src/resolvers/decisions.js`: expose visible task keys with a `taskLinked` boolean in history. Add `prepareRepairLink` and `repairConcernLink`. Preparation performs no writes. Confirmed repair re-reads the task, CAPA, current NC, and task links as the user. It recognises a `Relates` link to the CAPA in either direction and posts only if absent, then records link completion. The site-specific Relates type ID is discovered rather than hard-coded. If an earlier marker write failed on a known new task, repair lists and confirms that marker write too; a conflicting existing marker blocks repair.
- `src/frontend/DecisionDetails.jsx`: show **Repair link** for a visible saved task whose link completion is unrecorded. Add a **Confirm link repair** dialog and perform the write only after **Confirm repair**. Read-only viewers cannot initiate repair. Completed links no longer show the repair button.
- `manifest.yml`: add the optional decision attributes `taskLinkedAt` (string) and `taskMarkerVersion` (integer). Existing records remain readable without migration; no indexes or modules changed.
- `scripts/audit-dependency-paths.js`: reproducible static inclusion check of the four advisory-bearing leaf packages across the resolver and four UI entry points, without executing the bundles or uploading anything.
- `docs/SECURITY-DEPENDENCIES.md`: seven distinct advisory IDs, severities, installed versions, full dependency paths including shared/deduped parents, vulnerable-path reachability, registry-verified upstream fixes, and explicit accept/wait decisions. No `npm audit fix` or dependency version changes.
- `docs/tasks/T19.md`: this task record, scope evidence, validation and owner checks.

## Manifest and scope verification

**No new scopes.** `app.id` is unchanged. Only the two optional custom-entity attributes listed above were added. Forge's custom-entity documentation explicitly permits adding attributes to an existing entity; the existing attribute/index definitions were retained. See [Defining Custom Entities](https://developer.atlassian.com/platform/forge/storage-reference/entities-manifest/).

Verified with the Forge MCP `get-api-required-scopes` tool:

| Jira operation | Required classic scope already declared |
| --- | --- |
| `PUT /rest/api/3/issue/{issueIdOrKey}/properties/{propertyKey}` — task marker | `write:jira-work` |
| `GET /rest/api/3/issue/{issueIdOrKey}` — marker and `issuelinks` reads | `read:jira-work` |
| `POST /rest/api/3/issueLink` — create/repair Relates link | `write:jira-work` |
| `GET /rest/api/3/issueLinkType` | `read:jira-work` |
| `POST /rest/api/3/search/jql` | `read:jira-work` |
| `POST /rest/api/3/issue` | `write:jira-work` |
| `GET /rest/api/3/issue/createmeta/{projectIdOrKey}/issuetypes` | `read:jira-work` |
| `GET /rest/api/3/mypermissions` | `read:jira-work` |

The task-marker PUT and expanded task GET, issue-link POST, and link-type GET shapes were verified with `fetch-api-operation`. GET issue supports `fields`, `properties`, and `failFast`; repair requests `issuelinks` explicitly and refuses missing link data. The issue-link documentation states that a duplicate link request is treated as successful; together with the fresh pre-write check and no comment payload, this makes retries safe even if two repair invocations overlap. See [Issue properties](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-properties/#api-rest-api-3-issue-issueidorkey-properties-propertykey-put), [Get issue](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-issueidorkey-get), and [Create issue link](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issue-links/#api-rest-api-3-issuelink-post).

All Jira operations run `asUser()`. Existing `storage:app` covers custom-entity metadata. The marker write additionally needs the viewer's Edit Issues permission on the task, and link creation requires the relevant Link Issues permission; scopes do not bypass these project permissions. A missing permission does not cause replacement task creation.

## Documentation and runtime limits

No new Jira request shape, scope, or manifest attribute type remains unverified against Forge documentation. The Forge CLI, hosted schema rollout, live permission changes, Jira marker-write behavior, link races, and native UI rendering could not be exercised here. Tests simulate these conditions with the installed Forge SDK transaction builder and mocked Jira responses.

A task created successfully but whose creation response is lost before its ID is known cannot receive a marker in this invocation. Its new claim requires a marker, so summary alone cannot recover it; the app asks for manual Jira review and never creates an automatic replacement. If the task key was saved, a failed marker or link can instead be completed through the confirmed Repair link flow. Legacy claims without a usable claim timestamp retain the existing manual-review limitation.

Older saved task keys have no `taskLinkedAt`, even if their Jira link already exists. Repair verifies the existing link without posting another and records completion. It does not assume an old link exists merely because a task key was saved.

## Owner click/check walkthrough

1. In a development project, open an editable saved NC with a visible strong/related CAPA. Use a CAPA with no effectiveness evidence, or first confirm the recurrence. Open **QualityLoop** and click **Refresh evidence and decisions**.
2. Click **Effectiveness concern**, enter a reason, and click **Record decision**. In **Confirm follow-up task**, verify the project, task title, CAPA link, assignee, and the `qualityloop-followup` marker-property write are listed. Click **Keep decision only** to check that cancellation creates no task.
3. Repeat on another concern and click **Create task and link**. Open the task and verify one Relates link to the CAPA. Using the owner's authenticated Jira REST tooling, read the task's `qualityloop-followup` property and verify schema version 1, this decision ID, CAPA ID, NC ID, and durable claim timestamp. Refresh the NC's history: the task link should appear and Repair link should be absent after completion is recorded.
4. In a controlled development permission setup, allow task creation and editing but deny Link Issues on the task's project. Create a follow-up as above: the task key must remain in history after linking fails. Restore Link Issues, refresh history, click **Repair link**, and verify **Confirm link repair** lists only the intended task-to-CAPA Relates link (plus the marker write if it previously failed). Click **Cancel** first to verify no write occurs, then repeat and click **Confirm repair**. Verify exactly one Relates link, recorded completion, and the button disappearing after refresh.
5. For an older saved task whose link already exists but completion is unrecorded, click **Repair link** and **Confirm repair**. The app should verify the existing inward or outward Relates link, create no duplicate, and stop offering repair after refresh.
6. For a pre-T19 unconfirmed claim with a valid claim timestamp and exactly one visible legacy task, click **Check for task**. Verify the confirmation says **This task has no QualityLoop marker; confirm only if you know it is the follow-up task.** Cancel unless the task is known. A new claim with a same-summary unmarked task or another decision's marker must not offer that task. Recovery must still require confirmation before saving any key.
7. Open the read-only side view or use a viewer without Edit Issues on the NC: repair must not be actionable. Revoke access to a candidate/task between proposal and confirmation in a controlled test: no stored key or link write should result from a denied re-read.
8. Exact response-loss, marker-change, uniqueness, and concurrent/repeated-repair conditions are covered deterministically by `npm test`; they need not be reproduced by causing live network failures.
