## Resolver audit

There are **23** bridge resolver functions remaining. All Jira operations use `asUser()`, directly or through `userJira`; there is no production `asApp()` call. Forge KVS is app storage and has no `asUser()` API, so stored information is protected by Jira authorisation before disclosure.

Every issue resolver uses only `req.context.extension.issue.id` for the current issue; payload `issueId` and unexpected fields are rejected before I/O. Current-issue operations return `null` on denied/missing issue/property reads. Search candidates, historical CAPAs, counted NCs and linked task keys are freshly fetched asUser; denied candidates are omitted without their fields or counts. Error boundaries catch arbitrary exceptions and return fixed safe messages. Logs contain only a fixed operation name, never exception messages, stacks, issue IDs, field values or response bodies. Domain validation errors contain fixed application text only.

**Security-driven limitation:** historical T5 explicitly allowed app-context existence checks. T10's viewing-user rules supersede that exception. Jira's documented GET-issue 404 covers both missing and inaccessible issues, so a safe user-context orphan classifier cannot be implemented from that response. Manual orphan discovery/deletion is disabled, rather than risking deletion of inaccessible records. The admin page retains visible-record backfill. The existing deletion event and confirmed sample cleanup still remove associated stored records; missed deletion events may leave records with no manual orphan repair path in this release.

The `issue-deleted` handler is not a resolver. It validates event type, self-generated flag and numeric event issue ID, performs only storage cleanup, and catches/logs failures without event/record values. It has no Jira reads or user-facing response.

Removed bridge functions: **`probeWrite`, `probeRead`, `probeSearch`, `probeIssueAccess`, `probeJqlEscaping`, `e8PairState`**. Removed the security-test payload bypass, tracing and save/restore pathway from production capture/matching. No shipped caller depended on these paths.

## Documentation verification

Forge MCP guides verified platform, modules, manifest, backend and native UI usage before edits; component references checked the admin page's existing Stack/Text/Heading/Button props. Both operation and required-scope tools were called for every Jira REST route/method still used:

- GET/DELETE `/rest/api/3/issue/{issueIdOrKey}`
- GET/PUT `/rest/api/3/issue/{issueIdOrKey}/properties/{propertyKey}`
- POST `/rest/api/3/search/jql`
- GET `/rest/api/3/mypermissions`, `/rest/api/3/user`, `/rest/api/3/project/{projectIdOrKey}`
- GET `/rest/api/3/issue/createmeta/{projectIdOrKey}/issuetypes`, `/rest/api/3/issueLinkType`
- POST `/rest/api/3/issue`, `/rest/api/3/issueLink`
- GET/POST `/rest/api/3/issue/{issueIdOrKey}/transitions`

GET issue documents 404 as missing **or insufficient view permission**, which is why user-context 404s no longer select stored records for deletion. `read:jira-user` covers author lookup; the other Jira operations fit `read:jira-work`/`write:jira-work`; KVS requires `storage:app`.

No new manifest properties, API shapes or scopes remain unverified against Forge documentation. Forge CLI is absent from PATH and local npm binaries, so Forge schema/lint validation could not run. Live Jira rendering, permission changes, event delivery and installation behaviour remain unverified locally.

## Owner click/check sequence

Use an already installed build containing T10 when one is available; these live checks were not performed here.

1. Open a disposable Jira issue you can browse/edit, then **Apps → qualityloop**. Set up an NC, complete required fields, click **Save**, reload, and verify the original part string is preserved. Confirm no E1/E2/security/E8 controls appear in the panel or **QualityLoop evidence** issue-context view.
2. Use **project navigation → QualityLoop → Create sample scenario (5 issues)**. Inspect the five writes, cancel once, then reopen/confirm. Click **Check sample readiness** if needed. Open the linked new NC: DEMO CAPA-B should match; absent effectiveness evidence should be explicit; revisions/hints remain separate. Verify no real CAPA status changes.
3. On that NC's qualityloop panel, choose **Engineer-confirmed recurrence**, supply a reason and evidence, then **Record decision**. Reload and check author/history/state. Record an **Effectiveness concern** and inspect the follow-up dialog; cancel once and confirm no task was created. Confirm only if you intend the listed task/link writes.
4. Open the same decision in two browser tabs. Record from one, then submit the older version from the other. Verify a conflict refreshes current state without a duplicate append or duplicate task.
5. Repeat as a Browse-only user: capture and decisions are read-only. Restrict a matched CAPA or referenced NC, then refresh evidence/history. Its details and contribution to counts must disappear. Revoke access between preparing/creating a follow-up; expect no hidden identifiers or stack traces in the response.
6. In **Jira settings → Apps → QualityLoop data**, click **Scan accessible app records**. Only records whose NC and CAPA you can browse contribute to counts/backfill. Manual orphan deletion is visibly unavailable. Repeat as a non-admin: page is unavailable and direct resolver calls return no maintenance data.
7. On the project QualityLoop page, choose **Remove sample scenario**. Inspect the keys, cancel once, then reopen/confirm. Verify only listed, still-labelled registered samples are deleted. A lost label leaves its issue in Jira. Revoke Browse access before completion and verify no saved issue key appears in removal reports. Check Jira manually for remaining samples before creating another scenario.
8. Delete a disposable NC/CAPA through Jira and verify its associated decision/pair records are eventually removed by the existing deletion event (best effort). Check Forge logs only for fixed operation messages; no field values, issue IDs, exception stacks or response bodies should be logged. A missed event remains a documented cleanup limitation.
